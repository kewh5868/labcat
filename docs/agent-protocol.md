# Bounded assessment workflow

The research process owns retrieval, source validation, scoring and the retained
report. The model selects literal candidate names and supplies source-bound
qualitative interpretations. It cannot supply scientific measurements or replace
the report with generated prose.

## Required sequence

1. Interpret the request using the closed catalog and exact request spans.
2. Search the enabled public adapters. If the model requests a report before
   discovery, the server performs the existing bounded discovery stage once.
3. Attempt candidate selection from the returned documents. When eligible source
   documents exist, report generation is rejected until a proposal batch is
   attempted. Repeated premature requests remain rejected within the existing
   tool and time limits. An empty, valid proposal list records that no supported
   names were identified; it does not manufacture candidates.
4. Retain the first general application/use assessment. Perform the existing
   optional property follow-up once, then return selected-attribute review tasks
   with the available source context for the remaining assessment batch.
5. Generate the authoritative report. If offered general or attribute reviews
   remain and a batch/call is available, one assessment reminder can return the
   outstanding work. Ignoring that reminder cannot cause an unbounded loop.

The selection prerequisite is distinct from the single assessment reminder.
Trusted end-of-run recovery can retain an honest incomplete report if the model
terminates without completing this sequence. Such recovery does not emit a
successful model-requested `report_retained` marker. That marker requires an
actual, nonblocked report generated by the requested stage; it describes report
retention, not scientific completeness.

## Source-linked attribute review

The run-only `attribute_review` metadata uses version
`offered-attribute-review-v1`. Each offered task identifies an admitted candidate,
a positive-importance selected criterion, an approved retained document and source,
and an exact quotation anchor. It supplies no judgment, interpretation or property
value. The complete offered document and its retained method/section context are
the material to review; the anchor is only a selector into that text.

A task requires a complete sentence of 12–480 characters that passes the existing
literal candidate and criterion-context checks for an unknown judgment. This is
a conservative lexical review opportunity, not evidence that a positive or
negative interpretation is justified. Long sentences, missing local identity or
criterion context, and unavailable documents may produce no task. The underlying
retained sources are not rewritten, and this worklist does not weaken admission
rules or change historical `literature-fit-v1` or `literature-fit-v2` arithmetic.

Explicit request goals come before preset-only criteria; selected weights order
goals within that group. Tasks take one turn per candidate before adding a second
task for that candidate, and one document per criterion before alternate documents.
When a later-round slot is available, a positive-importance stability criterion
receives attention without replacing a candidate's sole goal. Zero-weight default
stability checks remain visible in the assessment context but are not forced into
the attribute worklist.

Validated target, functional application, processing, environment and identity-scale
spans accompany the tasks as **preferences, not evidence**. The selected criterion
goal remains authoritative. The model must distinguish applicable evidence from
an untested condition: an absent condition is unknown, while mixed requires actual
conflicting evidence for the criterion. A processing test alone does not establish
in-service durability. These instructions assist interpretation; lexical validation
does not establish semantic or scientific correctness.

## Capacity and accounting

The effective runtime retains its existing eight-tool/eight-turn limits, two
evaluation batches, 96-row envelope limit and 24 KB evaluation-argument limit.
The worklist adds no retrieval, model request or automatic retry. It offers at
most 16 attribute tasks, with a combined general-repair/attribute guideline of
24 rows. Twenty-four maximal ASCII rows fit below the input byte limit, but
Unicode and actual submitted lengths can reduce capacity; the byte validator is
always authoritative. Task selectors have an additional 8 KB reply budget.

With one batch remaining, `evaluation_phase` is `final_assessment`. Its guidance
combines outstanding general pairs, rejected-row corrections and the delivered
attribute tasks in that same call. `priority_criteria` lists the missing general
criteria and criteria present in the final task list. All selected preferences
remain available separately. `assessment_work` counts those general pairs and
current-reply tasks, repeats the 24-row guidance and marks itself as non-evidence.
It is recomputed after each document or task removal. Neither the counts nor the
worklist require fabricated unknown submissions or complete every task before a
partial report can be retained. Exhausted budgets return report-completion
guidance without inviting an additional assessment batch.

The entire reply, including preferences, feedback, tasks and complete documents,
must fit 28 KB of serialized UTF-8. After any document truncation, tasks are rebuilt
against only documents delivered in that reply or previously delivered during the
same run. A task cannot cite a dropped, previously unoffered paragraph. No source
text is cropped further to make a task fit. All originals remain retained on the
server under the existing document limits.

`retained_document_count` measures server context. `offered_document_ids` and
`offered_document_count` record actual successfully returned document IDs, while
`offered_retained_document_count` identifies the overlap with current context.
The reviewable, offered, reviewed, unattempted and withheld task counts are
separate. `unoffered_document_task_count` distinguishes a context-delivery gap from
other capacity limits. A retained assessment, including an explicit unknown,
counts as reviewed only for the matching candidate/criterion/document; rejected
submissions do not. Reading properties, constructing a worklist, or failing to
serialize a reply does not record delivery. These counts describe the assessment
process and never imply scientific confidence or completeness.

## Assessment completion diagnostics

New runs can include `candidate_evaluation.task_completion` in their execution
plan, using `assessment-task-completion-v1`. Before each actual evaluation
attempt, the parent snapshots the attribute-task selectors that it has
successfully delivered. Submitted rows are matched to those selectors while
the rejected arguments are still in memory. Only aggregate counts survive:
offered tasks, matched and unmatched rows, distinct submitted tasks, and tasks
not submitted in that batch. General application/use rows may be unmatched
because this worklist covers selected attributes.

Processed batches distinguish accepted unknowns, accepted non-unknowns,
already-retained rows, and rejections in six fixed categories: format, selector,
quote binding, criterion context, method, and requested goal. Task counts are
distinct from row counts. A task with several submitted rows can appear in
multiple outcome groups; accepted-task totals use their union. Unknowns count
as reviewed but do not provide property coverage. A non-unknown interpretation
can be support, mixed evidence, or a concern, and still needs scientific review.

These counts describe individual attempts, not cumulative completion. Tasks
already reviewed in an earlier batch may be absent from the next submission;
use the separate `attribute_review` totals for the run-level work remaining.
Later retrieval cannot backfill an earlier snapshot. A repeated successful
batch returns its existing feedback without another diagnostic record. A
transport or batch-limit rejection records a fixed uninspected state; a binding
failure retains submission counts without inventing row outcomes.

The optional envelope holds at most eight records, 192 delivered task selectors
per snapshot, and 96 submitted rows per attempt, with explicit saturation.
Selectors, names, source passages, model arguments and exception text do not
enter the stored diagnostic. It adds no model call, retrieval, retry, worker
instruction, scoring input or evidence. Older reports without the field remain
unchanged. Invalid optional counters are omitted when reading saved history;
the saved report and original archive bytes remain intact.
